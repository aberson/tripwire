tripwire · a preflight check for commands you are about to run

tripwire

A command-line tool that reads the command you are about to run — or the state of the folder you are about to work in — and tells you which known past mistake you are about to repeat, citing the written rule that mistake came from. It never runs the command you hand it, changes nothing, and it will not tell you a command is safe.

A preflight check for the mistakes you already wrote down

Most development advice is written down and then forgotten at the exact moment it matters. tripwire is the small, boring fix: two commands you run before the risky thing, not after. tripwire command explain -- <command> reads proposed command text and classifies it. tripwire check looks at the repository you are sitting in — wrong repo layer, a worktree on no branch, a stale branch, signs of another session already working here.

It carries ten rules, and a rule was only admitted if a written policy or a recorded incident already existed for it — the bar is deliberately high, because a checker that cries wolf gets ignored. It is Python with zero runtime dependencies (standard library only), it never runs the command you hand it (its repository check does shell out to read-only git), never sits between you and your shell, and never fixes anything for you. It also refuses the one thing every tool like this is tempted to claim: an unflagged command is reported as nothing matched, never as safe.

The receipt — every warning names the rule it came from

Below is real output from the installed command line, captured on 2026-09-05 and pasted here unedited. Read the last line of each block: that provenance: field is the point of the whole tool. A warning is not an opinion the program formed; it is a pointer back to the workspace policy document the mistake was written down in. Those documents live in the operator's dev workspace rather than in this repository, so the pointer is a citation rather than a link — but it names exactly what a reviewer would have to go read to argue with the rule.

try ituv run tripwire command explain [--json] -- <command>

A warning. Staging everything at a folder that contains other repositories quietly sweeps them in. tripwire says so, and offers the narrower form.

> tripwire command explain -- "git add -A" target: git add -A [warn] TW-GIT-001@v1: Changes are staged at a coding-root, where a broad `git add -A` or a bare `git stash` sweeps nested project repos. Prefer path-scoped `git add <paths>` / `git stash push -- <paths>` and verify the staged set before committing. Suggested: git add <specific paths>. observed: broad staging: git add -A provenance: .claude/rules/working-directory.md

warnexit code 0 — a warning is advisory and does not block

A blocking finding. Some commands throw work away with no way back. Those exit non-zero, so a script or an agent calling tripwire can stop on them.

> tripwire command explain -- "git push --force" target: git push --force [fail] TW-GIT-003@v1: Command performs a destructive git operation (`reset --hard`, `push --force`, `checkout -- <path>`) that discards work irrecoverably. Run a merge-base/ancestor check first and prefer a non-destructive alternative. Suggested: git push --force-with-lease after a merge-base/ancestor check. observed: git push --force provenance: .claude/rules/worktree-hygiene.md; docs/friction-catalog.md

failexit code 1 — the caller decides what to do with it; tripwire still runs nothing

A finding that names the safer form. Killing processes by name takes down whatever else happens to share that name. The suggested replacement kills one process tree by ID.

> tripwire command explain -- "taskkill /IM node.exe /F" target: taskkill /IM node.exe /F [fail] TW-CMD-001@v1: Command kills processes by name (`taskkill /IM`, `Stop-Process -Name`), which can terminate unrelated processes. Kill by PID with a tree kill (`taskkill /T /F /PID <pid>`). Suggested: taskkill /T /F /PID <pid>. observed: taskkill /IM <name> provenance: docs/lessons-learned.md (Subprocess tree-kill on Windows)

Ten rules, one registry, IDs that keep their meaning

All ten rules live in a single file, and both the repository check and the command explainer read their ID, severity, message and provenance from that one registry — a rule may expose one surface or both — so the two cannot drift apart about what is bad or why. Six are advisory, four are blocking. Every ID is versioned — TW-GIT-001@v1 — and a change in meaning bumps the version instead of silently redefining an existing ID, so an ID quoted in a note a year ago still means what it meant then. The written sources below are cited by path; like the provenance lines above, they are documents in the operator's dev workspace, not files in this repository.

It was graded before release — and it filed a complaint against itself

Before v1 shipped, a validation run drove the production command line as a subprocess — not the internals, the same thing an operator types — against six throwaway git repositories built with real git, each engineered to trip one named rule (two of them unavoidably carry a second, real finding — a linked worktree is by definition an active worktree); a frozen corpus of 22 risky commands; 25 clean trials; and a real, busy workspace. The report it produced is committed in the repository, so the numbers below are checkable rather than recalled.

What was testedTrialsResult
Seeded bad repository states, one per throwaway repo66 of 6 each detected at the expected rule ID
Risky commands, frozen corpus2222 of 22 at the expected rule ID and severity
Clean trials — one clean repo plus 24 safe commands250 false positives a 0.0% nuisance rate against a stated 5% ceiling
Live workspace check, best of three runs30.37 s against a 10-second budget

The harder question is what it does on a real machine that is genuinely messy. It raised three findings there — and the report argues each one, with the tool's own observed evidence, as a true positive rather than noise. Zero findings on a clean fixture, three correct ones on a busy workspace, is the behaviour you want; the two numbers only mean something together. (Paths and filenames are redacted in the committed report, and reproduced redacted here.)

TW-SES-001@v13 state file(s) at coding-root <dev-root>: .plan-expedite-state.* (filenames redacted)true positive — three real files left by other sessions

The part worth reading is section 6. The same report files one limitation against the tool: on a standalone repository with no coding-root marker above it, one probe reports unknown and returns a non-zero exit — on every run, forever, with nothing the user can do about it. That is the deliberate never-a-clean-pass contract working as specified, and it is also a guaranteed annoyance for anyone outside the layout it was built for. The report writes it down as a design tradeoff for a future version rather than quietly dropping the case — and the four criteria it checks off are the same four written into the plan before any of the work started.

One of seven tools that do not import each other

tripwire is one of seven local-first utilities for a development workspace, built under a constraint that is easy to state and annoying to keep: none of them share a runtime, and none of them import each other. Where two meet, the seam is a file-format contract — a command shape, a JSON report shape, an exit-code map — so any one of them can be replaced without touching the others.

The diagram at the top of this page is that map; below is the same map as a list. Every one of these runs entirely on your own machine: no rule is fetched from a server, and no finding is reported anywhere.
